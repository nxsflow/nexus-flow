# 2026-11-28 · NEX-173 · The decide procedure's open calls err towards the owner

- Decided by: coder on NEX-173
- Why: RFC 0010's "`nxs merge-gate decide`" leaves some engine-internal calls open, and each is taken so that the gate never gives pm what the owner should see. A verdict that is not valid is the only reason reported (step 2 decides there, as step 1 does), but the owner's approval of the head still counts, so the owner can approve a pull request no verdict covers. The changed paths are `git diff --no-renames --name-only -z` from the merge base to the head, so a rename always counts under both paths, whatever the machine's rename settings; with no merge base, every file of the head counts. CODEOWNERS is read from the git repository's top at the base, as GitHub reads it. When `default` is `pm` and a `pm` rule is met, both `default` and `pm_rule` are reported, in that order. `changes_requested` is reported once per owner, in the order of `owners`, with the login as the review spells it. `verdict_invalid`'s `detail` is a JSON array of strings, one per problem. A comments or verdict file the command cannot read gives no verdict, as a missing one does.
- Instead of: stopping on unrelated histories with a non-zero exit, which RFC 0010 does not list among the cases it cannot decide; git's rename detection, which a `diff.renames` setting changes; reporting only one reason when both `default` and a met `pm` rule let pm merge.
- Topics: merge-gate, git, codeowners
