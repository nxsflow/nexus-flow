# 2026-11-27 · NEX-139 · The seam's init returns the factory and genesis reports with the space's fields

- Decided by: coder on NEX-139
- Why: RFC 0006 and RFC 0004 have `nxs init` end with `nxs factory install` and then `nxs genesis create`, both without `--update`, and RFC 0004 asks the no-overwrite proof at the seam. So `nexus_flow_seam::init` and `init_with` run both after the space's step, on the root `nexus-flow.toml` marks, and return `Init`: the four fields of the store's `InitReport` as before (`space`, `created`, `sync`, `v1_workspace`), plus `factory`, the report `Engine::factory_install(false)` returns, and `genesis`, the report `Engine::genesis_create(_, false)` returns. A `tracked` GENESIS is not an error at the seam, as with `genesis_create`: the caller sees it in `genesis.is_refused()`. A failure of GENESIS's create is the new `Error::Genesis`, and `nxs` prints it with the codes `nxs genesis create` uses. The steps run in the RFCs' order, and the first that fails stops the rest; a rerun picks up where it stopped, since every step keeps what is there.
- Instead of: keeping `init_with` returning `InitReport` and running the installs only in `nxs`, which would leave a seam caller without the factory and GENESIS, against the parity decision; or nesting the store's report as a field, which would rename every existing `report.space` to `report.repository.space`.
- Topics: seam, init, factory, genesis, v2
