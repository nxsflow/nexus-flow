# 2026-11-27 · NEX-172 · The verdict is the json block on the first non-blank line after the first mark

- Decided by: coder on NEX-172
- Why: RFC 0010 says the mark is "followed by a fenced code block with the info string `json`" but not what may stand between them, nor what a comment with two marks means. The gate reads the comment as it reads GENESIS.md's owner-rules (NEX-77): the first line outside a fenced code block that is the mark, apart from surrounding whitespace, and a fenced block whose info string is `json`, apart from surrounding whitespace, that starts on the first non-blank line after it. Anything else there, such as a sentence or a block marked `text`, means the comment has no verdict, and the gate decides `owner`. The comments file is refused whole, so there is no verdict, when it is not a JSON array or an entry lacks a numeric `id`, a `user` (an object with a string `login`, or `null`, which is no verdict author), a `created_at` in GitHub's `YYYY-MM-DDTHH:MM:SSZ`, compared bytewise, or a `body` that is a string or `null`. Every narrowing errs towards the owner.
- Instead of: the first `json` block anywhere after the mark, which could read a code sample further down a comment as the verdict; skipping malformed entries, which could make an older comment the newest; parsing any RFC 3339 offset, which GitHub never sends.
- Topics: merge-gate, verdict
