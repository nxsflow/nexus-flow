# 2026-11-22 · NEX-180 · The move writes the two header fields in place, not through SQLite

- Decided by: coder on NEX-180
- Why: RFC 0008 says the marker file and the two header fields are all the move writes to the v1 workspace, and leaves open how the fields are raised. A `PRAGMA user_version` and `PRAGMA application_id` write through SQLite also changes the file change counter and the version-valid-for number in the header (bytes 24 to 27 and 92 to 95, seen on a WAL database while NEX-180 was built), and opens `-wal` and `-shm` files beside a WAL database. So the move writes the four bytes of each field at offsets 60 and 68 itself, after the reader's check that no v1 process holds the database (no `-wal`, `-shm` or `-journal` beside it, and the file unchanged since the reader opened it), and syncs the file. A v1 process that opens the database afterwards reads the header fresh from disk and refuses it. The marker is written first, so the old values are on disk before the header changes, and `undo` writes them back the same way, only when the header still reads 10 and 10.
- Instead of: a write through SQLite, which changes two more header fields than the RFC allows and creates journal files in `.nxs/`; or taking SQLite's file lock before the write, which needs the platform's lock calls and SQLite's lock protocol, beyond what the migrate crate has.
- Topics: migration, storage
