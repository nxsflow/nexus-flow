# 2026-11-22 · NEX-177 · The move reads db.sqlite immutable, and takes a journal file beside it as v1_in_use

- Decided by: coder on NEX-177
- Why: RFC 0008 asks the reader to change nothing and to refuse a workspace a v1 process holds open (`v1_in_use`), but leaves open how. v1 keeps its database in WAL mode, and an ordinary read-only SQLite connection to it still creates `db.sqlite-wal` and `db.sqlite-shm` (seen in the NEX-177 tests), so the reader opens the file with `immutable=1`, which takes no lock and creates no file. An immutable read does not see a write-ahead log, so the reader refuses while SQLite's `-wal`, `-shm` or `-journal` file lies beside the database: SQLite keeps them exactly as long as a connection is open, and one left by a process that ended uncleanly may hold writes `db.sqlite` lacks. It checks again after every read, and also refuses when the database file's length or modification time changed since it opened the workspace, so a v1 process that opened the database meanwhile, or opened, wrote and closed it between two checks, fails the read instead of tearing it.
- Instead of: an ordinary read-only connection, which leaves `-wal` and `-shm` files in `.nxs/`; asking the OS whether a process holds SQLite's byte locks, which needs a platform crate the migrate crate does not have and differs between macOS, Linux and Windows; or reading a leftover write-ahead log, which only v1's own open should recover.
- Topics: migration, storage
