[en]
On a DynamoDB relay, a change made in one window could be permanently missing in another when two pushes to the same stream overlapped: a reader could be handed the later push's position before the earlier push was written, and it never asked below that position again. The relay now takes an op's position in the same write that stores the op, and that write also checks that the op one position below is already stored, so a reader is only ever handed a position once every lower one is written, as on the SQLite and Postgres relays. A re-pushed op no longer leaves a gap in the positions either. **Upgrade step for DynamoDB operators: grant the relay's role `dynamodb:ConditionCheckItem` on the op table before you deploy this version** — without it every push fails with an access-denied error (a 500) while reads keep working. The wire protocol and the relay table are unchanged; no data migration is needed. Ops a replica already skipped before the upgrade are not fetched again by that replica. Also for operators: appends to one stream now take turns, so heavy concurrent writing to a single stream is slower than before, and a push now stops after 20 seconds with a 503 (set `NXF_RELAY_PUSH_DEADLINE_SECS` to change it), which the client simply pushes again; while older relays still write the same table they answer more pushes with a 500.
[de]
Auf einem DynamoDB-Relay konnte eine Änderung aus einem Fenster in einem anderen dauerhaft fehlen, wenn sich zwei Pushes in denselben Stream überschnitten: Ein Leser konnte die Position des späteren Pushs erhalten, bevor der frühere geschrieben war, und fragte danach nie mehr unterhalb dieser Position. Das Relay vergibt die Position eines Ops jetzt im selben Schreibvorgang, der das Op speichert, und dieser prüft zugleich, dass das Op eine Position darunter schon gespeichert ist — ein Leser erhält eine Position also erst, wenn jede niedrigere geschrieben ist, wie bei den SQLite- und Postgres-Relays. Ein erneut gepushtes Op hinterlässt auch keine Lücke in den Positionen mehr. **Update-Schritt für den Betrieb mit DynamoDB: Gewähre der Rolle des Relays `dynamodb:ConditionCheckItem` auf der Op-Tabelle, bevor du diese Version ausrollst** — ohne das schlägt jeder Push mit einem Zugriffsfehler fehl (ein 500), während Lesen weiter funktioniert. Wire-Protokoll und Relay-Tabelle bleiben unverändert; eine Datenmigration ist nicht nötig. Ops, die ein Replikat vor dem Update bereits übersprungen hat, holt dieses Replikat nicht nachträglich. Ebenfalls für den Betrieb: Appends in einen Stream kommen jetzt nacheinander dran, daher ist starkes gleichzeitiges Schreiben in einen einzelnen Stream langsamer als bisher, und ein Push hört jetzt nach 20 Sekunden mit einem 503 auf (änderbar über `NXF_RELAY_PUSH_DEADLINE_SECS`), den der Client einfach wiederholt; solange ältere Relays noch in dieselbe Tabelle schreiben, antworten diese öfter mit einem 500.
[migration.en]
Manual, DynamoDB relays only, before deploying: add `dynamodb:ConditionCheckItem` on the op table to the relay's IAM role (the op table now needs `Query`, `PutItem`, `UpdateItem`, `ConditionCheckItem`). Automatic: everything else — no table or data change. SQLite and Postgres relays need nothing.
[migration.de]
Von Hand, nur DynamoDB-Relays, vor dem Ausrollen: `dynamodb:ConditionCheckItem` auf der Op-Tabelle zur IAM-Rolle des Relays hinzufügen (die Op-Tabelle braucht jetzt `Query`, `PutItem`, `UpdateItem`, `ConditionCheckItem`). Automatisch: alles andere — keine Tabellen- oder Datenänderung. SQLite- und Postgres-Relays brauchen nichts.
